# B1 — The Glacier cost gotcha

`storage_class = "GLACIER"` means **S3 Glacier Flexible Retrieval**. It has a 90-day minimum
storage duration. If an object transitions on day 30 and is deleted on day 40, it has spent only
10 days in Glacier, so AWS bills its normal 10 days of storage plus a prorated early-deletion
charge for the remaining 80 days of the minimum. The charge is based on the object's billable
size and the Glacier Flexible Retrieval storage rate in the bucket's Region; there is no single
dollar figure without those inputs. Retrieval and request charges, if any, are separate. See
[AWS S3 pricing](https://aws.amazon.com/s3/pricing/) and
[S3 Lifecycle transition considerations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-transition-general-considerations.html).

Don't treat `days = 30` as a safe deletion window. Define a finite policy for when sellers may
request deletion, and fulfill all accepted requests before an object becomes eligible for
archival. For example, **if** requests are accepted through day 40 after upload and must be
completed within 30 days, mark an object archive-eligible only after the request window is closed
and it has no pending deletion request. A day-70 transition is then a conservative age guard:

```hcl
resource "aws_s3_bucket_lifecycle_configuration" "listing_media_archive" {
  bucket = aws_s3_bucket.listing_media.id

  rule {
    id     = "archive-eligible-listing-photos"
    status = "Enabled"

    filter {
      tag {
        key   = "archive-eligible"
        value = "true"
      }
    }

    transition {
      days          = 70
      storage_class = "GLACIER"
    }
  }
}
```

The application should set `archive-eligible=true` only after the deletion window has closed and
all accepted requests have been completed. The tag filter prevents unrelated bucket objects from
being transitioned; the current rule has no filter and therefore matches all objects. S3 Lifecycle
counts `days` from object creation (or, for versioned objects, the relevant version's creation),
not from when the tag was added. If the deletion window is measured from a later event, such as a
listing's sale, use application-managed eligibility based on that event rather than assuming
`days` starts when the tag changes.

This design depends on the day-40 request cutoff being an actual business rule. If sellers can
request deletion at any time, no fixed lifecycle age can guarantee that an archived object won't
be deleted during its 90-day minimum. Keep such objects in a more flexible storage class until
they are no longer eligible for deletion, or accept and budget for early-deletion charges. A
30-day processing SLA by itself is not a request cutoff.
