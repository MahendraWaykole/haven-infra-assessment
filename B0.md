# B0 — The `count` trap

Removing `"la-002"` changes the list from `["la-001", "la-002", "la-003", "la-004"]` to
`["la-001", "la-003", "la-004"]`. With `count`, Terraform identifies bucket instances by numeric
index, not by landlord ID:

| State address | Old bucket | New configuration at that address | Plan |
|---|---|---|---|
| `aws_s3_bucket.landlord_media[0]` | `haven-media-la-001` | `haven-media-la-001` | no change |
| `aws_s3_bucket.landlord_media[1]` | `haven-media-la-002` | `haven-media-la-003` | replace because "bucket" attribute is force-new, Terraform plans to destroy "haven-media-la-002" and create "haven-media-la-003" |
| `aws_s3_bucket.landlord_media[2]` | `haven-media-la-003` | `haven-media-la-004` | replace |
| `aws_s3_bucket.landlord_media[3]` | `haven-media-la-004` | no instance | destroy because arrey length dropped from 4 to 3 |

The bucket name is part of each S3 bucket's identity and changing it forces replacement. Thus,
instead of removing only `la-002`, the plan replaces the buckets previously belonging to `la-002`
and `la-003`, and destroys the `la-004` bucket. This is dangerous in production: buckets may hold
irreplaceable media, deletion can cause an outage or data loss, and a non-empty S3 bucket normally
prevents Terraform from deleting it (so the apply may fail partway through). Do not apply this
plan as the way to remove one landlord.

Use stable keys with `for_each` so each instance address is based on the landlord ID:

```hcl
resource "aws_s3_bucket" "landlord_media" {
  for_each = toset(var.landlord_accounts)
  bucket   = "haven-media-${each.key}"

  tags = {
    landlord_account_id = each.key
  }
}
```

Changing the resource's addressing scheme alone would make Terraform think the existing
`count` instances were removed and new `for_each` instances were added. Preserve state identity
with `moved` blocks. For the original four-account state, add all of these to the same module:

```hcl
moved {
  from = aws_s3_bucket.landlord_media[0]
  to   = aws_s3_bucket.landlord_media["la-001"]
}

moved {
  from = aws_s3_bucket.landlord_media[1]
  to   = aws_s3_bucket.landlord_media["la-002"]
}

moved {
  from = aws_s3_bucket.landlord_media[2]
  to   = aws_s3_bucket.landlord_media["la-003"]
}

moved {
  from = aws_s3_bucket.landlord_media[3]
  to   = aws_s3_bucket.landlord_media["la-004"]
}
```

Perform the migration in two steps: first keep all four IDs in `var.landlord_accounts`, change
the resource to `for_each`, add the `moved` blocks, and plan/apply the address-only migration.
Confirm the plan shows the instances moving to their keyed addresses without bucket replacement.
Then remove `"la-002"` from the variable and plan/apply again. That second plan should destroy only
`aws_s3_bucket.landlord_media["la-002"]`; verify its contents have been safely handled before
applying. `moved` blocks require Terraform 1.1 or later.

For this exercise, `terraform plan -refresh=false` compares the configuration with the seeded
state without attempting to contact AWS. A normal plan refreshes resources first; if the AWS
credentials lack access, the plan reports a refresh error rather than reliably showing this
state-addressing change. `-refresh=false` is appropriate for inspecting this seeded example, not
a replacement for a refreshed production plan.
